# Task-linked coworker messaging

The runtime provides authenticated `/v1/agent-messaging` APIs and the `scripts/agent-messaging.mjs` helper. Install the `skills/lark-agent-messaging` directory into the user's Codex skills directory (a local symlink is supported). Run the helper from the originating conversation and working directory; it uses `CODEX_THREAD_ID` and never asks for a token on the command line.

`send` accepts JSON on stdin with `recipientId`, `sourceLabel`, `text`, a stable unique `requestKey`, optional `chatId`, and optional `identity` (`bot` by default). It records the source thread and exact Feishu receipt. A retry with the same key returns the original record; changing its fields is rejected. A lost send response produces `send_unknown`, requiring inspection in Feishu rather than automatic retry.

Bot replies use the existing event listener. User-identity replies use the optional personal inbox polling collector. Search results are enriched with message references before routing. Both paths share the same durable routing store and exclude unrelated senders/chats/identities. A matching quoted message or known reply chain routes automatically. Recent unquoted personal replies also route automatically when there is exactly one eligible source conversation. Multiple-source unquoted replies and conflicting references go to the owner in Feishu and Forge `/agent-messaging`; there is no keyword/model attribution.

The bridge connects to the existing Codex daemon Unix socket, configurable via `LARK_AGENT_CODEX_SOCKET`. It reads the exact source thread and sends `turn/start` with **empty user input and standalone tool output**, preserving the message as third-party data. Codex queues this output when that thread already has an active turn. The bridge does not start another server, resume an unloaded thread, or override execution permissions. Separate desktop/CLI processes may own threads absent from the daemon; these are retained as `waiting_source`.

For those conversations the originating Agent runs `wait [seconds]` (maximum 86400) or `receive`, then `ack <ids...>` after receiving the result. A claim transaction prevents simultaneous automatic delivery; a lost claim remains visible and is not redelivered automatically. The shared skill documents keeping the terminal wait alive when a task depends on the colleague's answer. This is not an always-on desktop wake mechanism for independently hosted conversations.

Forge displays requests, assignment candidates, delivery receipts, uncertain sends and closed requests. Decisions require the displayed row version. Closing a request stops capturing new replies for it. A lost bridge response produces `delivery_unknown`; only an explicit owner decision retries it. Runtime restart converts incomplete sends/deliveries/claims into uncertain states. Database changes are additive; retain the configured database and its backups.

Bot messaging requires the bot's normal IM read/send permissions and group membership for groups. Sending as the owner additionally requires app approval and the matching user's OAuth `im:message.send_as_user` grant. Personal polling uses `im:message.p2p_msg:get_as_user`, `im:message.group_msg:get_as_user`, `search:message` and message read access. Credentials remain in the existing CLI profile and protected local runtime config; Forge receives only the runtime proxy token server-side.
