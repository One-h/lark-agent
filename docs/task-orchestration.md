# Delegated Tasks

The optional task-orchestration plugin adds an authenticated `lark_task_orchestration` tool to the existing Lark MCP catalog. The current agent decides whether to answer directly or delegate within the user's request, based on the benefit of independent work, parallelism, or a more suitable available engine. Explicit engine assignments and requests not to delegate take precedence. Follow-ups go to the original Worker. The scheduler does not classify requests or relax permissions.

## Pilot Setup

- Enable `LARK_AGENT_TASK_ORCHESTRATION=1` on the runtime and the separate engine host. Set `LARK_AGENT_TASK_ORCHESTRATION_CHAT_IDS` to the exact comma-separated pilot chat IDs. With the global setting off, an empty chat list grants no access. Without the deployment flag, the plugin is not mounted and no task tables or tools are installed. `LARK_AGENT_DISABLED_PLUGINS=task-orchestration` disables the feature without removing data.
- To allow all eligible group and direct chats, use the authenticated `PATCH /v1/settings` with `{"taskOrchestrationGlobalEnabled":true}`. It defaults to false and switches without a restart. Set it back to false to restore the original allowlist. This setting does not mount a disabled plugin, grant execution permission, or bypass group privacy.
- Use the existing private engine-host socket, token and matching default workspace. Configure `LARK_AGENT_ENGINE_HOST_ENGINES` on the runtime to include only the permitted backend engines. The host checks engines, models and policies, and can advertise additional operator-approved absolute directories via the JSON array `LARK_AGENT_TASK_ALLOWED_WORKSPACES`. This pins directory identity without creating a worktree. Resume requires proof for the same task, engine, policy and workspace.
- The host can open a dedicated Codex App Server process or connect to its own operator-specified `LARK_AGENT_TASK_CODEX_APP_SERVER_SOCKET`. Do not point it at the interactive runtime's socket. `LARK_AGENT_TASK_CODEX_MODELS` optionally lists allowed explicit model IDs; the server default works without a list. The four ACP engines use their existing operator-managed launchers.
- With `LARK_AGENT_RUNTIME_URL` set to the runtime's loopback URL on the engine host, opted-in retained foreground ACP sessions receive `lark_tools` with an original-turn-bound context. These sessions expose task orchestration and approval status, not the full host capability catalog. Background task sessions do not receive the foreground gateway.
- Start in an isolated workspace and test conversation. The scheduler permits three background runs globally, one per engine and one per task. Restricted Codex uses a verified native read-only sandbox with no network or MCP escalation; other ordinary requests need an operator-configured restricted launcher. A dispatch approval does not turn a restricted process into a trusted one. If the operation cannot be performed under the original profile, the Worker reports the blocker.

## Behavior

- **Dispatch:** specify the goal, constraints, deliverables, permitted resources and Worker engine, optionally a Reviewer engine or the requester. Existing trusted-session rules apply. Other callers go through task-level automatic review or manual approval before the Worker is queued. The versioned task contract and durable admission receipt are recorded separately from a foreground turn grant.
- **Follow-up:** the original requester can supply input to the same Worker. Supported in-flight steering uses a stable input ID; otherwise it stays queued for the next turn in the same engine session. A disconnected call is not assumed to be unaccepted. Expansions require authorization before being added.
- **Finish and review:** the Worker decides whether to deliver a result, explain that no further work is needed, or report a blocker. The runtime freezes text and declared files; it verifies full Git commit IDs and copies bounded regular files into the result version. The Reviewer sees that version, uses a plain-text verdict and is asked once in the same session when the conclusion is unclear. A human verdict must identify the result version and come from the requester. An amendment cannot apply a previously started review under outdated criteria. A rejected result does not auto-rework; the Agent can explicitly use a preauthorized single rework with the original Worker and feedback.
- **Recovery and posting:** the runtime reattaches by the original host generation and dispatch ID. An uncertain start or input is not replayed. A started reply without a receipt is checked by exact Feishu readback rather than resent. Group privacy and source identity are checked before dispatch and posting. Review state and delivery are separate.

Use the task tool's list action to obtain the current revision before a write. Concurrent changes, stale approval and old review callbacks are fenced by their versions. An old command with the same input can be read back without submitting it again.
