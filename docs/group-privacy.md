# Group privacy boundary

Group messages, including owner mentions and replies to existing Agent tasks, no longer enter the legacy full-tool responder. The standalone runtime enables this boundary unconditionally. Legacy retry, text/media retry, host capability invocation, and host group reply routes also refuse group execution. Group quotes are not expanded through cross-message history tools before the gateway.

The tool-free group worker receives only bounded text from the same chat (at most 20 records of 1200 characters), public model knowledge, and explicitly brokered company text. It starts a fresh ephemeral conversation with an empty working directory and a separate CODEX_HOME; only the user's model authentication file is copied into the control directory outside that working directory. Global skills, hooks, plugins, MCPs, apps and memories are not inherited. Child environment variables exclude runtime/host/API credentials. A named permission profile denies the filesystem by default and disables tool-command networking. Built-in tool requests are rejected. No fallback to the legacy responder occurs if isolation fails.

Company roots are an owner-controlled local setting at `/v1/group-privacy` (Forge `/group-privacy`). The default is an empty allowlist. The backend broker performs only bounded company search/read, using model-proposed keywords; the model itself has no tools: relative paths within approved canonical roots, bounded plain-text source/document formats, no symbolic or hard links, no dotfiles, personal/session/credential paths, databases or binary documents. Recognized credential-bearing contents are withheld. This filter is supplementary: **every generated draft and every company research result stays private until the owner approves the exact outgoing text**. Group audiences never receive automatic model output, promises, research results or operation output. Live web search is not enabled in this baseline.

The owner is privately notified and can edit/publish a draft, reject it, run bounded company research, or explicitly forward a group reply to its original Agent. Versioned decisions prevent stale/replayed approval. Publication is bound to the original chat/message and exact reviewed text, with idempotency and uncertain-result states. Forwarding approves only transferring that third-party message, not new authority for the receiving Agent.

An operation requires a separate explicit decision containing the exact company root and command argument array. The stored operation and approval hash bind that one attempt. The command is run inside the Codex OS sandbox, with company-root write access, filesystem deny elsewhere, credential/session denies, sanitized environment, networking disabled, timeout and output limits. Unsupported or denied sandboxes fail closed; no unsandboxed retry is made. Results stay on the private review page and require a separate reviewed group reply. Personal-category requests cannot execute through this channel. This baseline does not offer automatic deployment or unrestricted toolchain/network access.

Agent-originated direct group sends are proposals returning `awaiting_approval`; only publication gives them an actual platform receipt and opens reply routing. Personal one-to-one task-linked messaging continues to use the existing path. The gateway is a group-message boundary, not a global restriction on the owner's independently authorized desktop Codex conversations.

Data tables are additive. Interrupted analysis returns to owner review; interrupted sends/operations become uncertain and are never automatically retried. Configuration, draft review and execution endpoints require a nonempty runtime token; Forge proxies it server-side and rejects foreign-origin mutations. Review pages are loopback services for the local trusted user; this does not add authentication between mutually untrusted users sharing one OS account.

Before research or owner notification, the isolated worker triages attention separately from privacy category. Only an explicit `no_action` classification for a non-operation message is silently marked `ignored`, with the reason retained and no draft, notification, research, forward, publication or execution. Casual mentions do not inherently require attention. Requests, questions, follow-ups, task replies, mixed messages and uncertainty stay in owner review; missing/invalid attention defaults to uncertainty and model failures remain reviewable. This is probabilistic triage, not perfect detection, so ignored records remain visible in Forge's processed history. It never relaxes publication or execution approval.

Installation must distinguish the Forge workspace from company-data authorization. Forge shows an explicit scope form during first-run setup and in Settings; the current workspace can be filled as a candidate only, and nonempty scope changes require owner confirmation. An empty allowlist is supported and preserves group/public-only operation. The local runtime setting survives restart and can be cleared to revoke access. Paths are not compiled into code, inferred from installation location, or inherited through a Forge configuration restore. Installers must ask the deploying user for approved company directories rather than copying another user's paths.
